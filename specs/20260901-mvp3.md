# Redesign spec — unified cyber-cv-letter template

## 0. Provenance

`drafts/cyber1-cv-letter` and `drafts/cyber2-cv-letter` are two independent
prototype implementations of this template, already reviewed against each
other in `drafts/comparison.md`, `drafts/cyber1-improvement.md`, and
`drafts/cyber2-improvement.md`. This document designs one unified
implementation that keeps the good ideas from both, fixes the problems
those review docs identified, and is simpler and more consistent than
either — it is not a merge of the two, and neither draft's code should be
edited in place to produce it. An implementer may still open files under
`drafts/` to see how a specific problem was solved before; that's a
reference for figuring out logic, not something the new code or its
comments should cite. Prior specs (`specs/20260821-design-cyber.md`,
`specs/20260828-mvp1.md`, `specs/20260830-mvp2.md`) are superseded by this
document and are not referenced from anywhere in the new implementation.

## 1. Goals

One Typst package, two authoring workflows — hand-written `.typ` and
Markdown via Pandoc — converging on one rendering mechanism, so the two
workflows can't drift apart. Every design decision is judged against two
readers: a naive ATS text-extractor (linear, single-column, real text,
nothing decorative in the text stream) and a human reviewer giving page one
about six seconds (bold titles, scannable hierarchy, restrained color).

**Non-goals:** veraPDF validation (PDF/UA-1 is targeted by construction —
`--pdf-standard ua-1` — not independently verified against the full
standard), HTML/plain-text output beyond what Pandoc's own writers give for
free, and cross-page "keep together" grouping (a section header can be
orphaned at the bottom of a page from its first entry; known and
acceptable, not solved here).

## 2. Architecture decisions

### 2.1 Rendering mechanism

Full content-tree introspection: `cv()`/`letter()` walk the whole document
body once, split at H1/H2 boundaries, and re-emit fresh `heading()` calls
for the pieces they recognize. This is one mechanism end to end, not a mix
of Typst show-rule interception plus a separate manual walk for the one
relationship (heading immediately followed by its meta line) that show
rules can't express, since ordinary show rules have no sibling lookahead.
One mechanism means one mental model for a future reader, and it has two
concrete side benefits: freshly-constructed `heading()` calls are never
re-matched by any show rule, so PDF-UA-1 tagging/outline behavior needs no
recursion guard; and accent-color rotation across sections becomes a plain
loop variable (`section-index`) instead of a Typst `counter()` object
threaded through show-rule closures.

### 2.2 Module layout

Split responsibility into small, single-purpose files rather than one
large one:

- `content.typ` — generic content-tree helpers with no CV-specific
  knowledge: `flatten-text`, `split-last`, `join-content`,
  `split-paragraphs`, `get-children`.
- `entries.typ` — the section/entry parsing state machine:
  `extract-meta`, `render-entry`, `render-bullets`, `render-note`,
  `render-skills-row`.
- `marks.typ` — decorative drawing only: `draw-chevron`, `draw-cursor`,
  `draw-rule`, `draw-placeholder-logo`.
- `theme.typ` — design tokens (palette, accents, spacing, page geometry,
  font-weight table).
- `ats.typ` — `pdf.artifact` wrapping and PDF metadata setup. A dedicated
  module for accessibility-adjacent code, not scattered across the files
  that happen to need it.
- `fonts.typ` — font-chrome/font-body resolution.
- `icons.typ` — icon loading.
- `cv.typ` — page setup, header/footer rendering, and the top-level `cv()`
  that calls into `entries.typ`.
- `letter.typ` — `letter()`, reusing `cv.typ`'s header component.

### 2.3 Spacing

One base unit `u`, starting from `6.4pt` — carried over as a starting point
only; re-verify empirically once the new rendering mechanism is in place,
since prior pixel measurements don't automatically transfer across a
mechanism change. Roughly eight named spacing tokens, each a literal `N * u`
multiple, mechanically checked by a script (§7) rather than eyeballed —
this is what prevents a set of tokens that are meant to move together from
drifting apart independently over time.

Every block-level element sets `above: 0pt` and lets its own `below:` be
the one source of the gap that follows it. The one exception class: a
handful of call sites need a nonzero `above` as a deliberate floor, because
Typst's block-spacing collapse (`max(prev.below, next.above)`) is the only
way to guarantee a minimum gap regardless of what happens to precede that
element.

Token names and shared relationships: `space-paragraph` (the ambient
bare-paragraph gap, and the gap around a whole bullet list — Typst's `list`
has no separate above/below of its own, so it falls back to ambient
`par.spacing`), `space-bullet` (bullet-to-bullet within one list — its own
token so list rhythm can be tuned independently of the surrounding
paragraph gap), `space-entry` (entry-to-entry), `space-section-to-rule`
(gap between section-heading text and its rule — tighter than
`space-rule-to-content`, so a section heading reads as bound to its own
rule rather than floating between it and the previous section),
`space-rule-to-content` (gap between a section rule and what follows it —
at least `space-paragraph`, so content never sits closer to the rule above
it than a paragraph sits to its neighbor), `space-header-to-section` (gap
above every section header, including the first — one relationship
regardless of position), `space-header-line` (line-to-line gap within the
identity block, reused for the entry title↔meta stack), `body-indent`
(list/code-line horizontal indent). `letter()` reuses `space-paragraph`
directly for its own paragraph-to-paragraph gap — there is no separate
letter-specific spacing token. Keep only the live "why this token is shared
across these call sites" rationale inline next to each token; put any
"tried X pt, reverted" tuning narrative in a CHANGELOG instead.

### 2.4 Type scale

No centralized dict. Grepping the drafts confirms every visual role
(`name`, `tagline`, `contact`, `section-header`, `title`, `meta`, `date`,
`body`, `code-line`, `skills-label`, `note`, `footer`) is read from
exactly one call site — nothing is shared across roles — so a role-keyed
lookup table only adds indirection: a reader has to jump to `theme.typ` to
learn a `(font, weight, size)` triple that's used nowhere else. Instead,
each role's values are literals passed directly at its one owning
function, right where the role is rendered:

- `name` (`font-chrome`, `bold`, `20pt`), `tagline` (`font-body`,
  `regular`, `10.5pt`), `contact` (`font-chrome`, `regular`, `9pt`),
  `footer` (`font-chrome`, `regular`, `8pt`) — the header/footer renderer
  in `cv.typ`.
- `section-header` (`font-chrome`, `bold`, `14pt`) — the section-header
  show rule in `cv.typ`.
- `title` (`font-body`, `semibold`, `12pt`), `meta` (`font-body`,
  `regular`, `10.5pt`), `date` (`font-chrome`, `regular`, `9pt`) —
  `render-entry` in `entries.typ`.
- `body` (`font-body`, `regular`, `10.5pt`), `code-line` (`font-chrome`,
  `regular`, `9pt`) — `render-bullets` in `entries.typ`.
- `note` (`font-body`, `regular`, `9.5pt`) — `render-note` in
  `entries.typ`.
- `skills-label` (`font-chrome`, `medium`, `9pt`) — `render-skills-row` in
  `entries.typ`.

No separate documentation table duplicates these values elsewhere: a
table-plus-call-sites would be two sources of truth for the same twelve
numbers, which is the exact drift problem `check_spacing.py` (§2.3, §7)
exists to prevent for spacing tokens — removing the dict from code while
keeping an equivalent table in the spec would just relocate that risk.
(`check_spacing.py` never covered type scale anyway, only spacing tokens,
so dropping the dict loses no verification coverage.)

Role names are still a deliberate departure from both drafts' naming,
applied for consistency, and are used as identifier/comment naming
guidance at each call site above (not as dict keys) so a reader can always
tell which role a given call renders: `title` (not `job-title` —
`EXPERIENCE`, `PROJECTS`, `EDUCATION`, and `CERTIFICATIONS` all use H2
entries, so "job" is a misnomer for what this role actually labels),
`meta` (not `org-location` — matches `extract-meta()`/"meta line"
terminology used everywhere else), `date` (singular, matching every other
role name), `note` (not `comment`/`size-comment`/`detail` — a later polish
pass fully aligned this role, and every internal identifier that renders
it, with the `show-notes:` flag gating it, §2.7, rather than leaving the
flag renamed while the content role stayed `detail`), `code-line` (not
`tech-line`/`tech-stack line` — names what the source construct actually
is, a trailing inline-code-only paragraph, and stays generic enough to hold
more than a tech stack; the render-role name and the markup-contract's
description of the trigger use the same word).

One low-level helper, `render-text(font, weight:, size:, fill:, body)`,
resolves `weight` via `resolve-font()` (§2.5) against the `font` family
the caller already picked, and applies `text(...)`. The caller decides
`font-chrome` vs `font-body` itself — it already has both in scope as
parameters — so there's no `.font`-field dispatch to maintain; that
indirection only existed to serve the now-removed dict.

### 2.5 Accent and font-weight resolution

Accent presets are one dict of colour lists — `red`, `green`, `friggeri` —
so a single-colour preset and a multi-colour rotation share one code path
(`resolve-accent(value)` returns a list either way; a custom hex or hex
list is also accepted). **Default accent is `red` (`#af3a03`)**, not
green. Font-weight resolution keeps a `font-weight-families` table mapping
`"IBM Plex Mono"`/`"IBM Plex Sans"` to their separate Medium/SemiBold
family names — a real Typst font-loading quirk (IBM Plex ships Medium and
SemiBold as distinct families, not weight variants of the base family, so
requesting `weight: "medium"` on the base family would silently substitute
the nearest weight it can find) — via one `resolve-font(family, weight:)`
helper.

### 2.6 Variant, logo/meta extraction

`variant: "themed" | "plain"` is an explicit parameter on both `cv()` and
`letter()`, not a hidden global read of `sys.inputs` inside the token
module — every other option is threaded through explicitly, so this one
should be too. `letter()` also takes `show-icons` (a polish-pass addition,
mirroring `cv()`'s existing parameter of the same name) so the cover letter
can opt into the same contact-icon treatment as the CV; both default to
`false`.

Section names are freeform — no closed vocabulary, no compile-time
`assert` on the name. An earlier version of this design enforced a fixed
list (`SUMMARY`, `EXPERIENCE`, `PROJECTS`, ... plus documented synonyms) as
a deliberate ATS-defensibility measure, but a later pass dropped it: the
`assert` only ever gated the *name*, never fed into *how* a section
renders — that dispatch was always, and remains, 100% shape-driven (a
section renders as entries if its children include H2 headings, as a
skills row if its children are all `terms.item`, and as freeform paragraphs
otherwise). With no rendering behavior riding on the name whitelist, the
`assert` was pure friction for zero remaining benefit, and it blocked a
legitimate case — an author's own section name that just wasn't on the
list. `check_ats.py`'s `SECTION_ORDER` check (§7) already regression-tests
that this package's own example content's section names extract correctly
and in order; that test, not a compile-time gate on arbitrary user content,
is what actually catches an ATS-defensibility regression here. The heading
text is still upper-cased for display (`# Summary` renders as `SUMMARY`)
regardless of how the author capitalized it — a purely visual
normalization, unrelated to the vocabulary question.

Logo/meta-line extraction detects a `box`-wrapped `image` node inside the
meta paragraph, rather than requiring the author to wrap the image in
literal bracket characters as a signal to strip later — simpler, and avoids
a Pandoc-escaping edge case entirely.

### 2.7 Identity-field handling, decorative marks, notes

Identity fields (name, email, tagline, ...) are interpolated into the
Pandoc template as **content** (`[$email$]`), never as quoted strings
(`"$email$"`), then flattened to plain text inside the package via
`flatten-text()`. Quoted-string interpolation runs Pandoc's own
markup-escaping over values that are about to sit inside a Typst string
literal, not markup — producing artifacts like a literal backslash before
`@` in an email address. Content interpolation sidesteps the whole problem,
so there's no need for an escape-fixup pass over the author record.

**Decorative marks:**
- **Chevron** — fixed size (a plain constant, not measured via
  `context`/`measure()` against the ambient font/size), calibrated to read
  as large as it does in `drafts/cyber1-cv-letter` at its dominant call
  site (the section header, 14pt): roughly 8pt wide, 10pt tall, 0.6pt
  stroke. Treat these three numbers as another empirically-reverified
  constant once rendered, not a final answer derived from arithmetic alone.
- **Cursor** — fixed `em`-relative size, `0.6em × 0.7em`, no ambient-ratio
  derivation. Independent of the chevron decision above. The gap between
  the preceding text and the cursor (`cursor-gap` in `cv.typ`, shared by
  the header name line and the footer prompt) is `0.3em`, retuned across
  several rounds of feedback: the original `0.2em` produced the same
  *ratio* to the cursor's own (also em-relative) `0.6em` width at both the
  20pt name line and the 8pt footer prompt, but the resulting *absolute*
  gap at the smaller footer size (1.6pt) read as visibly narrower than the
  header's (4pt) despite the identical ratio. A fixed absolute `4pt`
  (matching the header) was tried next, closing that gap exactly, but was
  itself reverted once the trade-off was reconsidered — `cursor-gap` stays
  proportional to its own local text size at each call site (consistent
  with the cursor's own em-relative sizing) rather than becoming the one
  absolute-unit exception among otherwise-relative decorative marks.
  `0.4em` was tried as the em-relative replacement (footer gap 3.2pt), then
  settled at `0.3em` (footer gap 2.4pt) as the better balance between the
  two goals — comfortable at the small footer size, not overly wide at the
  large header size.
- **Entry date** — rendered in the *current section's accent color* and
  the chrome font (the `date` role, §2.4) — the same treatment as the
  skills-row label, not `muted` gray. Thread the current section's accent
  color into `render-entry` (already available as a plain loop variable per
  §2.1).

**"Notes" (was "master-CV comment", briefly "details"):** a Markdown
blockquote immediately following a bullet is a **note line**, rendered
only when the document is built with `show-notes: true`. Internal names:
`render-note` (the bullet-comment branch), `note-tint` (the muted
annotation colour, not `comment-tint`), the `note` role (§2.4). An earlier
polish pass renamed only the boolean flag (`show-details` → `show-notes`)
and deliberately left the content-role naming (`detail`/`render-details`/
`detail-tint`) alone; a later pass reconsidered that split and renamed the
content role to match, since "the flag is `show-notes` but the thing it
gates is internally called `detail`" was its own kind of inconsistency —
simpler to have one word for one concept throughout.

## 4. Design tokens

**Palette:** `bg #ffffff`, `fg #3c3836`, `muted #7c6f64`, `secondary
#076678`. **Accent presets:** `red #af3a03` (default), `green #157d00`,
`friggeri` (a 5-colour rotation: `#008194`, `#df0c3d`, `#ad6000`,
`#628000`, `#a133fa`). All five friggeri colours sit at, or just above, the
4.5:1 WCAG-AA floor by construction — the red-pink and purple entries were
mildly desaturated from an initial full-saturation tuning that read as
over-saturated/"flashy" against feedback, while teal/brown/olive were left
unchanged. Red-pink was tuned across three rounds of feedback, each nudging
further toward red and/or further desaturated (H338.6°/S100% →
H341°/S95% → H343°/S95% → H346°/S90%, all at L46%, each step narrowing the
hue's distance to true red at H360°/0° and/or lowering saturation) — each
step re-verified against the AA floor, not just eyeballed. Every
text-bearing colour must clear WCAG AA (4.5:1 against white) — enforced by
`check_contrast.py`, never eyeballed.

**Type scale:** not a centralized token category — each role's
`(font, weight, size)` lives inline at its one owning function, per §2.4.

**Spacing tokens:** the eight named tokens in §2.3, each a literal `N * u`
multiple of one base unit, checked by `check_spacing.py`.

**Page geometry:** A4 (top/bottom 16mm, left 24mm, right 18mm) and US
Letter (top/bottom 16mm, left 25mm, right 19mm), each with a 9mm mark
gutter for the chevron.

## 5. Markup contract

| Source construct | Renders as |
|---|---|
| YAML front matter | Header block: name, tagline, contact line, links |
| `# SECTION` (H1) | Section header + rule + chevron |
| `## Title \| Date` (H2) | Entry title, date right-aligned in current-section accent colour + chrome font |
| Emph-only paragraph right after an H2 | Meta line (`Org \| Location`); a leading image becomes the entry logo |
| Plain paragraph(s) after the meta line | Tagline/body prose |
| Bullet list | Description bullets |
| `> note` right after a bullet | Note line — rendered only when `show-notes: true` |
| Trailing inline-code-only paragraph | Code line |
| Definition list | Skills row: chrome-font label in current accent colour, one line, never a table/grid |

`CERTIFICATIONS, AWARDS & PUBLICATIONS` (§8's example content) is just a
section name choice, not a registered synonym of anything — a single
section for all three kinds of entry, rather than three single-entry
sections, kept simple by design. Since section names are freeform (§2.6),
it renders through the exact same entry-shaped dispatch path as any other
H2-bearing section, with zero name-based branches anywhere in
`entries.typ`.

**Image paths:** plain relative paths in Markdown content (e.g.
`logos/cyberdyne.png`), resolved against a `resource-path` set in the
Pandoc "defaults" file (§6) rather than Pandoc's raw working directory —
never root-absolute. Root-absolute paths are reserved for the package's
own internal asset references (icons), never author-supplied content.

## 6. Markdown/Pandoc workflow

### 6.1 This repo's own dev/CI build

Binaries live under `.venv/bin`; nothing is installed system-wide.
`pandoc` comes bundled inside `pypandoc_binary` — symlink its bundled
binary to `.venv/bin/pandoc` (one documented one-time step). The `typst`
PyPI package is Python-bindings-only (verified by downloading the wheel and
inspecting its contents — no console-script/CLI executable ships with it),
and no other package distributes the real CLI, so `typst` itself is
installed the same way both drafts already do it: download the official
prebuilt release binary from `github.com/typst/typst/releases` and copy it
to `.venv/bin/typst` (no sudo, no system path). Pin the exact version
together in `requirements.txt` (as a comment) and `typst.toml`'s `compiler`
field so they can't drift apart silently.

**Local Typst package registration, rooted inside the repo, not `$HOME`.**
`drafts/cyber1-cv-letter`'s `--root=/` OS-anchoring hack for Pandoc's
extracted-image temp path is real fragility in general (get it wrong and
every image/import in a document can silently break) — but see below for
why it's actually *safe* for this specific package's own layout, and
adopted deliberately rather than avoided. `drafts/cyber2-cv-letter`'s fix —
registering the package as `@local/cyber-cv-letter:0.1.0` — is correct, but
writes outside the repo into `~/.local/share/typst/packages`. Typst
supports an explicit `--package-path` override for where "local" packages
resolve from (the same concept is exposed at the Python-binding level as
`Compiler(package_path=...)`, confirming it exists). Use a repo-local
`.typst-packages/` directory containing a symlink to the repo root, created
by `make setup`, and pass `--package-path .typst-packages` on every
`typst`/Pandoc-pdf-engine invocation.

**Single-step Markdown build with `--root=/`, no intermediate `.typ` file.**
Pandoc's own pre-render step resolves and extracts every referenced image
to an OS-absolute temp path *before* an external `--pdf-engine` ever runs,
and always writes that absolute path — never a relative one — into the
Typst source it hands to the engine. A leading `/` there is Typst's
project-root-relative syntax, so `--root` must be the OS root for that path
to resolve at all. Whether this is *safe* to do for a whole document
depends on where the package's own root-absolute references live, and this
package's specific layout makes it safe:

- `icons.typ`'s `/icons/FontAwesome/...` path lives *inside* the real
  `@local/cyber-cv-letter:0.1.0` (or, post-publish, `@preview/...`) package.
  A root-absolute reference written inside an *imported package* resolves
  against **that package's own root**, never the compiling document's
  global `--root` — so this reference is entirely unaffected by whatever
  `--root` the top-level document build uses.
- `extract-meta()` (§2.6) never reconstructs the logo `image(...)` call —
  it keeps Pandoc's original parsed node unmodified, specifically to avoid
  re-deriving a path against the wrong lexical root. That node lives in the
  *main document body*, not inside the package, so it *is* governed by the
  document's global `--root` — which is exactly what makes `--root=/`
  resolve it correctly against Pandoc's OS-absolute extracted-media path.

(This is also why `drafts/cyber2-cv-letter`'s single-step build was
actually broken despite superficially doing the same thing: it reconstructs
the logo `image(...)` call *inside* a real `@local`-imported package file,
so that root-absolute reference resolves against the *package's* root
instead, and its single-step build silently drops the logo regardless of
`--root`. This package's design — keeping Pandoc's original image node
un-reconstructed, in the main document — sidesteps that failure mode
entirely.)

With that established, `pandoc/cv.yaml` and `pandoc/letter.yaml` (§3) are
Pandoc ["defaults" files](https://pandoc.org/MANUAL.html#default-files)
bundling `template`, `pdf-engine: .venv/bin/typst`, and the full
`pdf-engine-opts` set this package's markup contract needs —
`--package-path .typst-packages`, `--font-path fonts`,
`--pdf-standard ua-1`, and `--root /` — plus, on `cv.yaml` only, a
`resource-path` pointing at wherever the source `.md`'s images actually
live (`examples/markdown` for this repo's own build; Pandoc resolves a
relative image path against its own working directory, not the source
file's directory, so this is needed regardless of `--root`). The whole
build is one command:

```sh
pandoc mycv.md -d pandoc/cv.yaml -o mycv.pdf
```

with per-variant `--input` values layered on top via repeated
`--pdf-engine-opt=--input --pdf-engine-opt=key=value` pairs (each `--input`
needs two separate `--pdf-engine-opt` flags, since Pandoc forwards one
engine argument per occurrence). No intermediate `.typ` file, no cleanup
step. The direct-Typst workflow's Makefile rules are untouched — no Pandoc
extraction is involved there, so `--root` never applies to that path.
Pandoc still needs the real `typst` CLI binary for `--pdf-engine=typst`;
there's no way around that while keeping Pandoc itself responsible for
producing the PDF.

Default `make examples` builds the same 8-PDF matrix
`drafts/cyber1-cv-letter`'s Makefile already declares:
`{cv,cv-plain,cv-friggeri,letter}.pdf` × `{typst,markdown}` — cyber (red
accent, themed, default, `show-footer=true show-icons=true`), plain
(`variant=plain`, footer/icons stay off), friggeri (`accent=friggeri
accent-scope=first3 show-logos=true show-icons=true show-footer=true
show-notes=true` — the one variant demonstrating every opt-in feature at
once, including the note line), letter (`show-footer=true
show-icons=true`, matching the cyber CV variant's flags). These are literal
dependency rules in the Makefile, not a flag cartesian product. Note that
`show-footer`'s *function-level* default (`cv()`/`letter()`) stays `false`
— an opt-in feature, same as `show-logos`/`show-icons`/`show-notes` — it's
only this example build matrix that turns individual flags on per variant.

### 6.2 External end-user workflow

The scenario to design for: someone who isn't a Typst author obtains this
package, looks at `examples/markdown/cv.md`/`letter.md` as reference, and
wants to write their *own* CV in a *separate* directory elsewhere, running
`pandoc` there against this package — without keeping their project nested
inside a clone of it. One mechanism covers this repo's own build and
external use alike: a Pandoc "defaults" file is just a YAML file referenced
by path (`-d path/to/pandoc/cv.yaml`), so an external user copies
`pandoc/cv.yaml` (or `pandoc/letter.yaml`) and its neighboring
`pandoc/cv-template.typ`, adjusts `pdf-engine`/`--package-path` for their
own environment (a system-installed `typst`, no `--package-path` at all,
`resource-path` pointed at their own images directory), and runs the same
one-command build. This replaces an earlier, more complicated design built
around Pandoc's *bare* `--template=NAME` lookup and its `.typst`-extension
requirement (`<pandoc-data-dir>/templates/NAME.<writer-extension>`,
verified empirically, along with a bare-HTTPS-URL `--template` fallback) —
both real, verified Pandoc mechanisms, but unnecessary complexity once the
whole build (template *and* every engine flag) travels together in one
defaults file referenced by explicit path. The template files are named
`cv-template.typ`/`letter-template.typ` (§3), matching every other Typst
source file in this repo — `.typst` was only ever needed for the
now-dropped bare-name lookup, not for anything else.

Document two consumption modes in the README:

- **This repo's own examples/tests** — §6.1, fully local and offline.
- **External use** — copy `pandoc/cv.yaml`/`pandoc/letter.yaml` and their
  neighboring template file, adjust `pdf-engine`/`--package-path`/
  `resource-path` for the target environment. Once this package is
  published to Typst Universe, the template's own
  `#import "@preview/cyber-cv-letter:<version>"` line resolves
  automatically through Typst's own package-fetching, and `--package-path`
  drops out of the defaults file entirely — nothing to install beyond
  `typst` and `pandoc` themselves.

The repo's own dev templates import `@local/cyber-cv-letter:0.1.0`
(resolved via `--package-path .typst-packages` per §6.1); templates as
distributed for external/published use import
`@preview/cyber-cv-letter:<version>` instead — a one-line difference
expected at publish time, not a design inconsistency.

## 7. Verification

Three scripts, one `make test`/CI target, nothing left unwired (fixing
`drafts/cyber1-cv-letter`'s own gap, where only one of its three scripts
ran from `make test`):

- `check_contrast.py` — WCAG AA against every `theme.typ` colour token.
- `check_spacing.py` — asserts every spacing token is a literal `N * u`.
- `check_ats.py` — extraction acceptance checks with two independent
  libraries (pypdf, pymupdf): linear reading order, this package's own
  example section names each on their own line and in order, intact
  contact strings, no private-use-area/replacement glyphs, no decorative
  characters leaked into extracted text, cross-workflow parity (the `.typ`
  example and the `.md` example extract identically). This is a regression
  check against this package's own known example content, not an enforced
  vocabulary — section names are otherwise freeform (§2.6). One file, two
  entry points: a `--all` CLI for ad-hoc runs, and pytest-discoverable
  functions for CI.

`tests/test_contrast.py`, `tests/test_spacing.py`, `tests/test_ats.py` are
thin wrappers importing the corresponding `scripts/*` module, so `pytest`
alone finds and runs everything. `.github/workflows/test.yml` installs
dependencies, downloads the pinned `typst` release binary into
`.venv/bin`, runs `make setup` (package-path symlink), then `make examples
&& make test`.

## 9. Typst Universe publish readiness

Complete `typst.toml`: `name`, `version`, `entrypoint`, `authors`,
`license = "AGPL-3.0-or-later"` (flagged as a verify-before-submit step
against Typst Universe's current accepted-license list — MIT/Apache-2.0 as
the fallback if AGPL is rejected, not resolved in this document),
`description`, `repository`, `keywords`, `categories`, `compiler` pinned to
the exact `typst` release version used in §6.1, an `exclude` list dropping
`.venv/`, `.typst-packages/`, `tests/`, `scripts/__pycache__`, and unused
alternate font families (`Roboto`/`SourceSansPro`) if package size is a
concern, and a `[template]` section pointing at `examples/typst`. Recall
from §6.2 that the published-package import string changes from
`@local/...` to `@preview/...` at publish time — expected, not an
inconsistency to fix.

**Preview images.** `typst/packages`' review process expects a rendered
preview alongside source, not source alone — a `make thumbnails` target
compiles all four typst-workflow example variants (`cv`, `cv-plain`,
`cv-friggeri`, `letter`) with `--format=png` into `thumbnails/`, the
default-variant `cv.png`/`letter.png` referenced from `typst.toml`'s
`thumbnail` field. The markdown-workflow examples get no separate
thumbnails — cross-workflow parity tests (§7) already guarantee they render
identically to their typst counterparts. Confirm the exact
filename/size/aspect-ratio conventions `typst/packages` expects against its
own contribution docs at implementation time rather than guessing — a
required pre-submission step alongside the license check, not optional
polish.

**Known limitation, documented rather than solved:** a published package
can't make a consuming document's own build automatically add its bundled
fonts to Typst's font search path (`--font-path` is a consumer-side
compiler flag, not something an imported package can set for itself).
Universe consumers without `IBM Plex Mono`/`IBM Plex Sans` installed
system-wide will see Typst's normal automatic-fallback substitution, not a
build failure; this repo's own dev/test build (§6.1, which passes
`font_paths`/`--font-path` explicitly) is unaffected.

## 10. Naming/terminology summary

| Old (either draft) | New |
|---|---|
| `cv-resume()` / `cv()` | `cv()` |
| `cv-letter()` / `cover-letter()` | `letter()` |
| "resume" (in prose) | "CV" (always) |
| `font` / `header-font` | `font-body` / `font-chrome` |
| `paper-size` | `paper` |
| `master` (bool) | `show-details` (bool), later renamed `show-notes` (bool) in a polish pass |
| type-scale role `job-title` | `title` |
| type-scale role `org-location` | `meta` |
| type-scale role `dates` | `date` |
| type-scale role `comment` / `size-comment` | `detail`, later renamed `note` (role, `render-note`, `note-tint`) to match `show-notes` fully |
| "tech-stack line" / "tech line" | `code-line` (role name and markup-contract wording, both) |
| default accent `green` | `green` remains a preset; **default is now `red`** |

`variant`, `accent`, `accent-scope` are explicit parameters on both `cv()`
and `letter()`, never a hidden `sys.inputs` read.
