# MVP Spec: Typst CV & Cover Letter Template

Status: draft, spec-only (no implementation in this pass)
Depends on: `specs/20260821-design-cyber.md` (visual design system, binding), `specs/20260821-rev-modern-cv.md` (structural/API lessons, advisory — follow only what makes sense)

## 1. Overview & goals

A single-column, ATS-friendly, visually distinctive Typst package for software-engineering CVs and cover letters. It implements the full visual design system from `20260821-design-cyber.md` (palette, type scale, spacing scale, page geometry, ATS rules, PDF/UA-1 target) and borrows the structural lessons from the `modern-cv` teardown in `20260821-rev-modern-cv.md` — real heading semantics, clean library/template separation, sane component defaults — without inheriting its ATS defects (icon-only labels, name-as-link-text) or its API hygiene problems (dead parameters, ad-hoc spacing, divergent CV/letter styling).

The defining constraint that supersedes both source specs where they'd otherwise conflict: **one markup-driven rendering path**. Entries are plain Markdown/Typst markup — a level-2 heading, an italic meta line, an optional paragraph, an optional bullet list — never a function call like `resume-entry(...)`. This is what lets the same content file work unchanged through both the direct-Typst workflow and the Markdown-via-Pandoc workflow.

Two consumers of this template exist and must produce visually identical output from the same underlying design tokens:
- **Public CV** — what goes to employers.
- **Master CV** — the same content, plus per-bullet detail comments (`> ...`) rendered in very light gray, for the author's own reference/expansion library.

## 2. Non-goals

- No i18n / multi-language support. Single English profile only. `modern-cv`'s `strings:`-dictionary escape hatch is explicitly not carried over — all copy is hardcoded English in the library.
- No component-function content API (see §1). Document-level *configuration* (theme, fonts, paper, feature toggles) is still a function call — see §7 — but entry *content* never is.
- No web/HTML output target in this MVP (design-cyber.md §10 describes one; out of scope here, see §15).

## 3. Package structure

```
typst.toml                  # package manifest — license: MIT (permissive, standard for
                             # Typst Universe; bundled font files keep their own
                             # upstream SIL OFL license notices, not relicensed)
lib.typ                     # single entrypoint, re-exports everything a template needs

src/
  theme.typ                  # design tokens: spacing scale, type scale, palette presets
                              # (default/red/friggeri), accent-scope (full/first3)
  fonts.typ                   # font-chrome / font-body resolution: fonts/<Family>/ lookup
                              # with system-font fallback (§8)
  layout.typ                 # page setup, header block, footer, section rule + chevron
                              # drawing, the entry-grouping engine (§6)
  icons.typ                   # icon loading + filename-derived alt text (§9)
  ats.typ                     # pdf.artifact wrapping helpers, PDF/UA-1 + metadata setup (§11)

template/
  cv.typ                      # Typst template entry point for a CV
  cover-letter.typ            # Typst template entry point for a cover letter

fonts/
  IBMPlexMono/                # new, downloaded (default font-chrome)
  IBMPlexSans/                # new, downloaded (default font-body)
  SourceSansPro/               # existing, kept as an alternate family
  Roboto/                      # existing, kept as an alternate family

icons/
  fontawesome/                 # existing set, files renamed to semantic names (§9)

examples/
  typst-default/               # hand-authored .typ, Sarah Connor, default theme
  markdown-default/            # equivalent .md + build command, same theme, via Pandoc
  markdown-frigerri/           # .md, icons:true, logos:true, accent:friggeri,
                                # accent-scope:first3
```

Rationale: mirrors `modern-cv`'s proven `lib.typ` + `template/` shape (familiar to Typst Universe reviewers) while staying flatter — 5 `src/` modules instead of `modern-cv`'s many per-section files, because our "sections" are user-authored content, not library code that needs its own file per section.

## 4. Design system

Binding source: `20260821-design-cyber.md` §4–§6. Reproduced here with the deviations from §14 folded in as notes.

### 4.1 Palette

| Token | Light/print | Notes |
|---|---|---|
| `bg` | `#ffffff` | |
| `fg` | `#3c3836` | 11.6:1 AAA |
| `muted` | `#7c6f64` | 4.87:1 AA — dates, locations, master-CV comment text baseline (see §10 for the lighter tint actually used for comments) |
| `secondary` | `#076678` | 6.60:1 AA, links |
| `surface` | `#fbf1c7` | tinted panels — web only, unused in PDF output |

Accent — **build-time selectable**, three presets:

| Preset | Print value | Notes |
|---|---|---|
| `green` (default) | `#157d00` | 5.29:1 AA |
| `red` | `#af3a03` | 6.12:1 AA |
| `friggeri` | 5-colour rotation: `#008194`, `#eb0054`, `#ad6000`, `#628000`, `#a638ff` | section headers cycle through the list in document order; see `accent-scope` below |

`accent-scope`: `full` (default) colours the whole section-header keyword; `first3` colours only the first three letters of the keyword (chevron and rule stay full accent regardless). Independent of the accent preset — "friggeri style" means setting both: `accent: friggeri, accent-scope: first3`.

### 4.2 Type scale

`font-chrome` and `font-body` are configurable (§8); the roles below are unchanged from design-cyber.md, just decoupled from a fixed family name.

| Role | Family | Size/weight | Case | Color |
|---|---|---|---|---|
| Name | chrome | 20pt Bold, +0.04em tracking | Upper | `fg` |
| Tagline | body | 11pt Regular | Sentence | `muted` |
| Contact lines | chrome | 9pt Regular | — | `fg` |
| Section header | chrome | 11pt Bold, +0.08em tracking | Upper | `accent` |
| Entry title (job/project title) | body | 11pt SemiBold | Sentence | `fg` |
| Meta line (org · location · dates) | body | 10.5pt Regular, **italic** (deviation, §14) | Sentence | `fg` |
| Body/bullets | body | 10.5pt Regular, leading 1.35 | Sentence | `fg` |
| Per-role tech line | chrome | 9pt Regular | — | `muted` |
| Master-CV comment | body | 9.5pt Regular, leading 1.3 | Sentence | very light gray, see §10 |
| Skills label | chrome | 9.5pt Medium | — | `accent` |
| Footer | chrome | 8pt Regular | — | `muted` |

Body text floor: never below 10pt. Ligatures off everywhere in the PDF output (extraction-safety, per design-cyber.md §5).

### 4.3 Spacing scale

Unchanged from design-cyber.md §4: base unit `u = 4pt`. Bullet-to-bullet `0.5u`, entry-to-entry `2u`, section-to-section `3u`, rule-to-first-entry `1.5u`, header-block-to-first-section `4u`. Per §5/§10, `list` and `quote` blocks inside an entry body share the same `0.5u` spacing constant so a bullet followed by a master-CV comment reads at the same rhythm as bullet-to-bullet.

### 4.4 Page geometry

| Property | A4 (default) | US Letter |
|---|---|---|
| Page | 210 × 297 mm | 216 × 279 mm |
| Top/bottom margin | 16 mm | 16 mm |
| Text column left edge | 24 mm | 25 mm |
| Right margin | 18 mm | 19 mm |
| Mark position | 15 mm from edge | 16 mm |

Structural rules unchanged: single column, top-to-bottom, no tables/grids/sidebars, nothing meaningful in header/footer.

## 5. Markup convention

This is the binding content contract. It applies identically whether the source is hand-written Typst or Markdown run through Pandoc's Typst writer — both produce the same standard Typst elements (`heading`, `emph`, `paragraph`, `list`, `quote`, `image`), which is what the entry-grouping engine (§6) intercepts.

```markdown
---
name: Sarah Connor
tagline: AI Security Engineer · Adversarial ML & Red Teaming
email: sarah.connor@ena.one
phone: +1 555 0142
location: Austin, TX
links: [ena.one, github.com/sconnor, linkedin.com/in/sarahconnor]
---

# SUMMARY

Security engineer specializing in adversarial robustness and red-teaming of
production ML/LLM systems. 8+ years across offensive security and applied ML.

# EXPERIENCE

## Senior AI Security Engineer | Jun 2023 – Present

*![](logos/cyberdyne.png) Cyberdyne Systems | Austin, TX*

Leading red-team engagements against internal LLM-powered products before launch.

- Built an automated prompt-injection fuzzing harness that surfaced 40+
  high-severity jailbreaks across 6 production LLM features before release.
  > Harness: custom mutation engine over a 12k-seed corpus, integrated into
  > the release-gate CI job; findings triaged with the app-sec team weekly.
- Led adversarial robustness reviews for a fraud model serving 2M
  requests/day, cutting evasion success rate from 18% to under 2%.

`Python · PyTorch · Burp Suite · Kubernetes · OPA/Gatekeeper`

# SKILLS

Security
: Adversarial ML · Red teaming · Threat modeling · Penetration testing

ML/AI
: LLMs · PyTorch · Prompt injection defense · Model extraction resistance
```

Element-by-element contract:

| Source construct | Renders as | Rule |
|---|---|---|
| YAML front matter | Header block | `name` first, always. `links` rendered bare (no scheme). |
| `# SECTION` (H1) | Section header + rule + chevron | Text must be from design-cyber.md §7.2's closed vocabulary — template fails the build otherwise. |
| `## Title \| Date` (H2) | Entry title + right-pushed date, one line | Split on the *last* `\|`; right side is the date. |
| Paragraph **entirely** wrapped in emphasis, immediately after the H2 | Meta line (`Org \| Location`) | Split on the *last* `\|`. A leading `![alt](path)` inside the emphasis is extracted as the entry logo (§4.4 grid), not rendered inline; alt text is auto-derived from the Org name text, not the markdown alt attribute (which stays empty by convention, e.g. `![]()`). |
| Plain paragraph, immediately after the meta line | Tagline (optional) | At most one; a second plain paragraph in the same position renders as an additional plain paragraph rather than being dropped. |
| Bullet list | Description (optional) | Hanging indent, `•` marker. |
| `> comment` immediately after a bullet, same list level | Master-CV comment for that bullet | Only rendered when `master: true` (§7); otherwise emits nothing. Blockquotes are reserved exclusively for this — do not use them for any other purpose in entry bodies. |
| Trailing inline-code paragraph (`` `A · B · C` ``) | Per-role tech line | Mono, muted, last element of the entry. |
| Definition list (`Term\n: values`) | Skills row | One line per row: label (fixed-width chrome box) + values, not a table/grid. |

## 6. Entry rendering engine

A top-level show rule receives the whole document body and processes it in three passes:

1. **Split into sections** at H1 boundaries. Validate each H1's text against the closed vocabulary (§7.2 of design-cyber.md); fail the build on anything else.
2. **Split each section into entries** at H2 boundaries (Experience/Projects/Education/Certifications) — sections without H2s (Summary, Skills) are rendered directly.
3. **Pattern-match the block sequence within one entry**, in order: `[required emph-only paragraph = meta line] [optional plain paragraph = tagline] [optional list = description, where each item may be followed by a quote = master comment] [optional inline-code paragraph = tech line]`.

Two viable implementation strategies for step 3 (either is acceptable; choose based on what proves tractable once `typst` is actually installed and the exact metaprogramming API is exercised):

- **(a) Full content-tree introspection** — walk `it.children`, dispatch on `it.func()` for each block, build the entry layout from the matched sequence directly.
- **(b) State-machine** — a Typst `state()` value tracks "what block type did we just render" so each element's own show rule (`show emph: ...`, `show list: ...`, `show quote: ...`) can decide its own rendering without seeing the whole tree at once.

Malformed input handling: any block that doesn't match an expected position in the sequence is rendered as a plain paragraph rather than silently dropped, so authoring mistakes are visible rather than invisible.

## 7. Configuration reference

Set via one top-level template call, e.g. `#show: cv.with(...)` in Typst, or the equivalent Pandoc metadata/`-V` variables when going through the Markdown path. This is document-level setup, not the entries API §1 forbids.

| Parameter | Type | Default | Effect |
|---|---|---|---|
| `paper` | `"a4"` \| `"us-letter"` | `"a4"` | Page size + margins (§4.4) |
| `accent` | `"green"` \| `"red"` \| `"friggeri"` \| hex | `"green"` | Accent color(s) (§4.1) |
| `accent-scope` | `"full"` \| `"first3"` | `"full"` | Section-header accent coverage (§4.1) |
| `font-chrome` | family name | `"IBM Plex Mono"` | Chrome role font (§8) |
| `font-body` | family name | `"IBM Plex Sans"` | Body role font (§8) |
| `icons` | bool | `false` | Icons before header contact fields (§9) |
| `logos` | bool | `false` | Reserved logo column on every entry (§5, §4.4) |
| `master` | bool | `false` | Render blockquote comments (§5, §10) |

## 8. Fonts

`font-chrome` and `font-body` are independent parameters, not paired presets — either can point at any family under `fonts/<Family>/`, or at a system-installed family name if no matching folder exists (Typst's normal font-resolution fallback; no special handling needed in `fonts.typ` beyond passing the name through).

- **Default**: `font-chrome: "IBM Plex Mono"`, `font-body: "IBM Plex Sans"` — matches design-cyber.md's type scale exactly (true monospace chrome). To be downloaded (SIL OFL) from the official IBM Plex GitHub releases into `fonts/IBMPlexMono/` and `fonts/IBMPlexSans/` in the build session.
- **Already-bundled alternates**: `"Roboto"` (chrome) and `"Source Sans Pro"` (body) — usable immediately with zero downloads. Note: Roboto is not a true monospace face; using it for `font-chrome` is a documented approximation, not a design-cyber.md-compliant substitution.
- Mixing is allowed and supported (e.g. `font-chrome: "IBM Plex Mono", font-body: "Source Sans Pro"`); the spec makes no claim about how well arbitrary combinations look together beyond the two documented pairings above.

## 9. Icons

Off by default (`icons: false`). When enabled, renders inline before each header contact field only — a separate feature from per-entry logos (§4.4/§5).

Convention: `icons/<set>/<semantic-name>.png`. Alt text = filename without extension. Rename mapping to apply to the existing set in the build session:

| Old filename | New filename | Semantic key |
|---|---|---|
| `fa-envelope-square.png` | `email.png` | `email` |
| `fa-phone-square.png` | `phone.png` | `phone` |

## 10. Master CV mode

`master: false` by default (public CV). When `true`, blockquotes immediately following a bullet (§5) render in very light gray directly under that bullet, at 9.5pt with 1.3 leading (§4.2). "Very light gray" is deliberately several steps lighter than `muted` (`#7c6f64`) — a print-safe gray around `#b8b2a8`–`#c2beb5` (build session should verify final AA/contrast doesn't matter here since this is annotation content never intended to ship to an employer, but should still be print-legible for the author's own reference).

Because `list` and `quote` blocks share the same `0.5u` spacing constant (§4.3), the flat/same-level blockquote choice from the answered question doesn't produce visible spacing artifacts even though Pandoc parses "bullet, comment, bullet, comment" as several one-item lists interleaved with quote blocks rather than one continuous list.

When `master: false`, the `quote` show rule renders `none` — zero output, zero space, identical mechanism regardless of whether the quote arrived via hand-written Typst or Pandoc-generated Typst. **Constraint: blockquotes are reserved exclusively for master-CV comments** — do not use them for any other purpose in entry bodies, since anything in a `quote` block is either suppressed entirely or rendered as a light-gray annotation.

## 11. ATS & PDF/UA-1 compliance

Binding, from design-cyber.md §7–§8 plus the applicable modern-cv rewrite requirements (R1/R2):

- Single column, no tables/text boxes/sidebars.
- Section names from the closed vocabulary only (§7.2 of design-cyber.md); build fails otherwise (§6).
- Nothing meaningful in page header/footer.
- Text-selectable PDF, fonts fully embedded and subsetted, no images of text.
- Contact details as real text at the top; name on line 1.
- One date format throughout (`Jun 2023 – Present`).
- Standard bullet characters (`•`).
- Reverse-chronological ordering.
- PDF/UA-1 conformance target (requires Typst ≥ 0.14), tagging on, every decorative element wrapped in `pdf.artifact` with the most specific kind, **every image carries alt text** (logos: auto-derived from org name, §5; placeholders: no alt needed since `pdf.artifact`-wrapped decoration).
- PDF metadata: `title` = `<Name> — <Role> — CV`, `author` = full name, `subject` = target role, `keywords` = core tech keywords.
- Filename convention: `Firstname_Lastname_CV.pdf` / `Firstname_Lastname_CoverLetter.pdf`.

## 12. Build & verification tooling

Prescribed method for the follow-up build session: a Python venv with

```
pip install pypandoc_binary typst pypdf pymupdf
```

- `pypandoc_binary` bundles a pandoc binary — covers the Markdown-via-Pandoc workflow.
- `typst` (PyPI wheel bundling the Rust binary) — covers the direct-Typst workflow and compiling Pandoc's output.
- `pypdf`/`pymupdf` — used to write an automated ATS-style acceptance check: extract text from a compiled example PDF and assert (a) it reads in the correct linear order (name → contact → summary → experience …), (b) it contains no orphaned/unprintable glyphs from icon fonts, and (c) the closed-vocabulary section names appear as plain extractable text. This mirrors design-cyber.md §11's "extraction reference" idea as a repeatable, automatable check rather than a manual one.

Both `typst` and `pandoc` are pinned to specific versions in the venv (`requirements.txt` or equivalent) per design-cyber.md §9.4's version-pinning guidance; minimum Typst version is 0.14 (PDF/UA-1 requirement, §11).

## 14. Explicit deviations from source specs

- **Entry markup shape** overrides design-cyber.md §9.2's own contract (`### Title` + em-dash-split org/location/date paragraph). This spec uses `## Title | Date` + a fully-italicized `Org | Location` meta line instead, per explicit instruction. Visual output still follows design-cyber.md's type scale/spacing as closely as possible.
- **Meta line is italic** — not present in design-cyber.md's type scale table (which has org/location/date as plain regular text); added as a legibility cue distinguishing the meta line from the tagline paragraph below it.
- **Section headers are H1, entries are H2** — design-cyber.md's own example uses H2 for sections and H3 for entries; shifted down one level here to keep entries fixed at H2 per instruction, with no ambiguity between the two.
- **Logo column** is new — not present in design-cyber.md at all. Layered on top of the existing entry structure per §4.4/§5.
- **`font-chrome`/`font-body` as independent parameters** rather than `modern-cv`-style paired presets — a deliberate simplification/generalization beyond what either source spec prescribes.

## 15. Out of scope for MVP / follow-ups

- Per-section logo toggle (currently global on/off only).
- Per-role font mixing beyond the two independent parameters already supported (no per-heading-level override).
- Accent presets beyond `green`/`red`/`friggeri`.
- Web/HTML output target (design-cyber.md §10).
- **Open item, not yet confirmed:** design-cyber.md §9.3 describes `plain` (motifs/accent stripped) and `txt` (plain text) build variants alongside the default `themed` variant. These weren't explicitly requested for this MVP. Recommendation: include them, since they're low-cost given the show-rule architecture (a `theme: "plain"` config value that zeroes out accent/rules, plus a trivial `pandoc --to=plain` target) — but this needs a confirmation pass before the build session commits to it.
