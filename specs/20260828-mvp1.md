# MVP Spec — Typst CV / Cover-Letter Template

This is the buildable spec. It resolves every conflict and open question left by its two inputs
(the design-cyber aesthetic/ATS spec and the modern-cv reverse-engineering teardown), plus one
requirement neither anticipated: entries authored as `## Job Title | Date` with an optional
company logo inline in an italicized meta line. Where this document repeats content from the
inputs, treat this document as authoritative; where it is silent, the design-cyber spec (§1–§5,
§7–§8, §11) still applies verbatim and is cited rather than restated.

---

## 1. Scope & non-goals

**In scope:**

- **Output: PDF only**, from two authoring workflows — direct Typst (`.typ`) and Markdown+Pandoc.
- Both documents: CV and cover letter.
- Full variant surface: `variant=themed|plain`, `accent=red|green|friggeri|<custom list>`,
  `accent-scope=full|first3` — every combination a one-flag build, no content edits
  (design-cyber §9.3).
- Optional inline company logos on Experience entries (new requirement, §5 below).
- Optional contact icons, reusing the existing `icons/fontawesome/` assets, off by default.
- Two selectable font families (IBM Plex, new default; Roboto/SourceSansPro, existing, kept as
  an alternate).
- PDF/UA-1 targeted **by construction** (Typst 0.14+ tagging, `pdf.artifact` on decoration) —
  not verified in this MVP.

**Explicitly out of scope / deferred, so it isn't silently dropped:**

| Item | Why deferred | Follow-up |
|---|---|---|
| HTML / plain-text (`.txt`) output targets | Output scope is PDF-only per user decision | Design-cyber §9.1/§9.3's second and third pipeline legs; would need a separate CSS/plain-text spec |
| §10 web token bridge | Explicitly out of scope for this task | Design-cyber §10 stands as-is for a future site spec |
| veraPDF / PDF-UA-1 conformance verification | "Target by construction, don't verify" — a deliberate MVP cut, not an oversight | Add a `make verify-ua1` target once veraPDF is wired into CI |
| Logo image alt text | User instruction: logo `image()` calls carry no alt/description | Known, accepted gap against full PDF/UA-1 image conformance (§5, §9) |
| ISO-8601 date opt-in | Carried over from design-cyber §6.5 as available-but-unbuilt | Not wired into the MVP template; document only |
| DOCX output | Design-cyber §7.4: generate `plain` variant PDF instead, DOCX only if explicitly demanded | No Pandoc DOCX target in the MVP Makefile |
| i18n / localisation | Already dropped in rev-modern-cv §2.10/§7.5 R5.6 | English string constants only, no `strings:` override needed for MVP (single language) |

`variant=txt` from design-cyber §9.3 does not carry over: it was an *output-format* choice
(Pandoc `--to=plain`), not a Typst-level content variant, and output scope here is PDF-only. Not
a silent gap — recorded here explicitly.

## 3. Design tokens

Imported from design-cyber §4 verbatim; summarized here for implementer convenience.
**`src/tokens.typ` is the single source of these values — do not hardcode a hex or size anywhere
else in the package.**

**Palette** (design-cyber §4.1–§4.2): `bg #ffffff`, `fg #3c3836` (11.6:1), `muted #7c6f64`
(4.87:1 — the AA floor, do not lighten), `secondary #076678` (6.60:1). `accent` is a build-time
selection, not a fixed token:

| Preset | Value | Contrast on white |
|---|---|---|
| `red` | `#af3a03` | 6.12:1 |
| `green` (default) | `#157d00` | 5.29:1 |
| `friggeri` (5-colour rotation) | `#008194 / #eb0054 / #ad6000 / #628000 / #a638ff` | all ≥4.51:1 |
| custom list | implementer-supplied | must be verified against the AA floor by the same method (§4.2) — not eyeballed |

`accent-scope=full|first3` (design-cyber §6.4, §4.6) controls whether the whole heading or only
its first 3 letters take the accent colour; independent of which `accent` preset is active.

**Spacing scale** (design-cyber §4.4): base unit `u = 4pt`. Bullet-to-bullet `0.5u`, entry-to-entry
`2u`, section-to-section `3u`, rule-to-first-entry `1.5u`, header-block-to-first-section `4u`.

**Type scale** (design-cyber §5.3): full table carried over unchanged — name 20pt Mono Bold,
section header 11pt Mono Bold accent, job title 11pt Sans SemiBold, org/location 10.5pt Sans,
dates 9.5pt Mono muted, body 10.5pt Sans, tech line 9pt Mono muted, skills label 9.5pt Mono
Medium accent, footer 8pt Mono muted. Ligatures off throughout (§5.4 — extraction fidelity).

**Marks** (design-cyber §4.5): drawn chevron and block cursor, both 0.6pt stroke, one monospace
grid cell, `accent`-filled, wrapped in `pdf.artifact`. `src/marks.typ` owns the two mark
primitives; nothing else draws a mark.

## 4. Markdown contract (revised)

This supersedes design-cyber §9.2's entry example. The grammar below is native Typst markup
(§11) — Pandoc's Typst writer emits exactly this shape from Markdown, so the contract describes
both the Markdown source *and* what a direct-Typst author types by hand.

```markdown
---
name: Sarah Connor
tagline: AI Security Engineer · Adversarial ML & Detection
email: sarah@example.com
location: Los Angeles, CA
links: [example.com, github.com/sconnor, linkedin.com/in/sconnor]
---

# Experience

## Senior AI Security Engineer | Jun 2023 – Present

*[![](logos/cyberdyne.png)] Cyberdyne Systems | Los Angeles, CA*

Cut adversarial-example detection latency 4x by rewriting the [batch, heads, seq, seq]
scoring path to run inline with inference rather than as a post-hoc batch job.

- Built a red-team harness that found 12 prompt-injection classes missed by the prior
  eval suite, raising the pre-release catch rate from 61% to 94%.
- Led migration of the model-serving detection pipeline to a streaming architecture,
  cutting p99 alert latency from 4.2s to 380ms.

`PyTorch · vLLM · Triton · Kubernetes`

# Skills

Detection
: Adversarial example detection · Anomaly scoring · Red-teaming

Infra
: Kubernetes · Terraform · Triton · CUDA
```

| Source construct | Renders as | Rule |
|---|---|---|
| YAML front matter | Header block (§6) | `name` emitted first, always |
| `# Heading` | Section header + rule + drawn chevron | Text must be in the §8 closed vocabulary — the `heading.where(level: 1)` show rule (`src/markup.typ`) **fails the build** on anything else |
| `## Job Title \| Date` | Entry title line | Split on the **last** `\|` — a title containing `\|` is theoretically possible and the last-split rule protects against it |
| Paragraph immediately following, fully italicized: `*[![](logos/x.png)] Org \| Location*` | Meta line (org · location · optional logo) | Logo image reference is optional and, if present, is the first inline element; remaining text splits on `\|`. No alt text is read or required (§5, §9) |
| Plain paragraph following the meta line (no bullets) | Optional tagline / one-line impact statement | |
| Bullet list following | Description bullets | `•` / `-` markers only (design-cyber §3.5) |
| Trailing inline-code-only paragraph | Optional per-role tech line | Mono 9pt `muted` — unchanged from design-cyber §9.2, unaffected by the entry-format change |
| Definition list | Skills rows | Overrides Pandoc's default `#terms` grid rendering — **verify this first**, per §11's implementation-risk note; getting it wrong silently reintroduces the grid structure design-cyber §6.6 bans |

**Heading levels, resolved.** Sections are `# H1` (was `##` in design-cyber §9.2); entries are
`## H2` (was `###`). The closed-vocabulary fail-the-build check moves with sections to the H1
show rule. This also satisfies design-cyber §8's PDF/UA-1 requirement that the document open
with a level-1 heading (rev-modern-cv R2.2) — the section headings *are* the H1s, so this holds
automatically once the header block itself is not marked as a heading.

## 5. Logo / photo spec

**Deliberate, explicit deviation from design-cyber §6.1.** §6.1 states an absolute rule: "No
tables, no `grid()`, no text boxes, no sidebars, no floating elements" and "No raster images and
no embedded `image()` files" for CV content. The logo feature violates both clauses on purpose,
scoped as narrowly as possible:

- **Geometry.** Each Experience entry's meta line renders as a `grid(columns: (auto, 1fr))`: a
  fixed **8mm × 10mm** logo cell, then a flexible text cell carrying `Org | Location`. The cell
  is reserved for **every** entry once `show-logos: true` is set — filled with the image if the
  entry's meta line has one, or a bordered placeholder (`muted` stroke, `pdf.artifact`) if it
  doesn't. This matches the "space always reserved, same dimensions" requirement.
- **Off by default.** `show-logos: false` is the shipped default on both `cv-resume()` and the
  Markdown front-matter equivalent. The residual risk below only applies to documents that
  explicitly opt in — the default, safest path never touches a grid.
- **No alt text.** The logo `image()` call carries no alt/description parameter, per explicit
  instruction. This is a known, accepted gap against full PDF/UA-1 image-alt-text conformance —
  consistent with §9's "target by construction, don't verify" stance, now extended to "don't even
  fully target it for this one non-decorative image." Decorative marks elsewhere need no alt text
  because they're drawn paths, not images (design-cyber §8); the logo is a genuine `image()`
  call and is the one element in the whole document this doesn't hold for.

**Residual risk — unverified, flagged rather than assumed away.** Rev-modern-cv §4.6 found that
`modern-cv`'s two-up flexible-box layout extracts cleanly because "the gap here spans most of a
180mm measure — orders of magnitude above any space-insertion threshold." The logo cell here is
~8mm, not 180mm — two orders of magnitude smaller. That reassurance **does not automatically
carry over** to a narrow grid gutter. This must be checked with the §11.2-style extraction test
(design-cyber) on the actual built example, with `show-logos: true`, before shipping — not
assumed safe by analogy to a differently-scaled layout. If `pdftotext -layout` inserts a spurious
space or line break between the logo cell and `Org | Location` that survives, the mitigation is
to widen the gutter or fall back to stacking logo above text rather than beside it — a decision
deferred to that test's outcome, not pre-decided here.

**One toggle, one rendering path.** Because there is a single markup-driven rendering path (§11),
"does the toggle work for direct Typst too" is not a separate question: the same `markup.typ` show
rule handles image / placeholder / off-state regardless of which workflow produced the grid's
input markup.

## 10. Build pipeline

### 10.1 Font loading mechanics

Typst has no in-language "load this font file as a usable family" primitive — font discovery is
a compiler-level concept via `--font-path` (or system-installed fonts). This is a constraint, not
a preference, and is documented here so it is not rediscovered by trial and error:

- Direct-Typst workflow: the Makefile always invokes `typst compile --font-path fonts ...`.
- Markdown+Pandoc workflow: the Makefile always invokes
  `pandoc ... --pdf-engine-opt=--font-path=fonts ...`.
- An author never needs to know either flag exists. `font:` / `header-font:` parameters on
  `cv-resume()` / `cv-letter()` select the family **name** (must match a family folder name under
  `fonts/`); switching families is a one-parameter change, not a build-flag change, since it
  doesn't touch ATS-relevant structure — directly satisfying the "fonts are configurable"
  requirement (rev-modern-cv §2.3 `font`/`header-font`, kept).

### 10.2 Pipeline

```
sarah-connor-cv.typ ──── typst compile --font-path fonts ──────────────────► cv.pdf
sarah-connor-cv.md  ──── pandoc --pdf-engine=typst --template=src/pandoc/template.typ
                                 --pdf-engine-opt=--font-path=fonts ────────► cv.pdf

sarah-connor-letter.{typ,md} ── same two targets ───────────────────────────► letter.pdf
```

### 10.3 Makefile targets

- One target per {workflow} × {document} × {paper size A4/Letter} × {variant/accent combination
  the example ships with}. Minimum: `cv-a4`, `cv-letter`, `letter-a4`, `letter-letter` for each
  of the two workflows, plus `cv-plain`, `cv-red`, `cv-friggeri` (etc.) to prove the one-flag
  variant surface (§9.3 of design-cyber, carried over).
- `make all` builds every combination; `make clean` removes generated PDFs only.
- No veraPDF target in the MVP Makefile (§1, §9).

## 11. Setup API + markup reference

### 11.1 Architecture: one shared markup convention, no per-entry function API

**Rejected:** a `cv-entry()` / `cv-section()` function-call API that the direct-Typst workflow
calls directly and the Markdown workflow reaches via a separate AST-pattern-matching adapter.
Two parallel implementations of entry rendering is exactly the kind of drift this MVP is meant to
avoid.

**Adopted:** there is exactly **one** authoring convention — the heading/paragraph/list shape
specified in §4 — and it is native Typst markup, not a Markdown-only artifact. A direct-Typst
author writes the same shape by hand inside a `.typ` file (`= Experience`, `== Senior AI Security
Engineer | Jun 2023 – Present`, an `_[..]_`-wrapped meta paragraph, a plain tagline paragraph, a
bullet list) inside the scope of a single `#show: cv-resume.with(...)` call. `src/markup.typ`
defines show rules keyed on Typst's native elements — `heading.where(level: 1)`,
`heading.where(level: 2)`, `list`, and a paragraph-shape match for the italic meta line — and
those rules **are** the entire entry-rendering mechanism, for both workflows.

The Markdown/Pandoc workflow is a thin on-ramp onto that same mechanism, not a parallel
implementation: Pandoc's Typst writer already emits idiomatic native Typst (`= Heading`,
`#emph[..]`, `#image(..)`, `- item`) from Markdown source. `src/pandoc/template.typ` wraps the
converted `$body$` in `#show: cv-resume.with(author: ..., ...)` (parameters populated from YAML
front matter via Pandoc template variables) and passes the body through **untouched** — no
adapter logic, because the same show rules in `src/markup.typ` fire on it directly.

`cv-resume()` and `cv-letter()` remain as functions, but strictly for **document-level setup**:
author identity, accent, variant, paper size, margins, and feature toggles. Neither function is
ever called per-entry.

### 11.2 Implementation risk to prototype first

Distinguishing "the meta-line paragraph immediately after an entry heading" from "an ordinary
tagline paragraph" is not a per-element show-rule match in isolation — Typst show rules match
individual elements, not sequences. The implementation needs a body-level show rule (or a
`context`-based walk over the top-level content sequence) that groups each
`heading.where(level: 2)` with the paragraph immediately following it, so the meta-line's italic
paragraph can be distinguished from the plain tagline paragraph that may follow it.

**This is the one mechanism to verify works before the rest of the template is built on top of
it.** Build a minimal two-entry prototype exercising this grouping first; do not proceed to full
`markup.typ` until it's confirmed. Flagged here the same way design-cyber flags its own
definition-list override (§9.2 there, §4 here) as "the one item worth verifying first."

### 11.3 `cv-resume()` signature

| Parameter | Default | Effect |
|---|---|---|
| `author` | required | Identity/contact record — name, tagline, email, location, links |
| `accent` | `"green"` | `"red"` \| `"green"` \| `"friggeri"` \| custom colour list (§3) |
| `accent-scope` | `"full"` | `"full"` \| `"first3"` (§3) |
| `variant` | `"themed"` | `"themed"` \| `"plain"` (§3, design-cyber §9.3) |
| `paper-size` | `"a4"` | `"a4"` \| `"us-letter"` |
| `margins` | design-cyber §6.1 table | Full record if overridden |
| `font` | `"IBM Plex Sans"` | Body family name — must exist under `fonts/` (§10.1) |
| `header-font` | `"IBM Plex Mono"` | Chrome family name — must exist under `fonts/` |
| `show-logos` | `false` | Company logo grid on Experience entries (§5) |
| `show-icons` | `false` | Contact-line icons from `icons/fontawesome/` |
| `show-footer` | `false` | Decorative footer prompt (design-cyber §6.8) |
| `body` | positional | Document content, authored per §4/§11.1 |

### 11.4 `cv-letter()` signature

Shares `author`, `accent`, `accent-scope`, `variant`, `paper-size`, `margins`, `font`,
`header-font`, `show-footer` with `cv-resume()` (§7 — same header component). Adds `date` (long
form) and `body` (the four-paragraph letter content, plain paragraphs — no heading/entry markup
needed since a letter has no sections or entries).

## 12. Verification checklist

Adapted from design-cyber §11, scoped to what's in this MVP.

**Build**
- [ ] `make all` produces every {workflow} × {document} × {paper} × {variant/accent} PDF, no warnings
- [ ] `variant=plain` and each `accent=` value build with no content edits (one-flag builds)

- [ ] `pdftotext -layout` on both example CVs (Typst-built and Markdown-built): section keywords
      each on their own line, no decoration characters, name is line 1

- [ ] Each experience entry's title/org/dates extract adjacent, in order
- [ ] **With `show-logos: true`:** rerun the same extraction and confirm the logo grid does not
      corrupt the `Org | Location` line (§5's flagged residual risk) — this is the one new check
      this MVP adds beyond design-cyber §11.2

**Cross-workflow parity**
- [ ] Direct-Typst and Markdown+Pandoc builds of the same example content are visually equivalent

**Human factors**
- [ ] Print/view greyscale: hierarchy still reads without colour (design-cyber §4.3, §11.5)

**Explicitly out of scope for this MVP, kept as a documented follow-up list (not forgotten):**
- [ ] veraPDF validation against PDF/UA-1
- [ ] Upload to 2–3 independent ATS simulators
- [ ] Screen-reader read-through

## 14. Example content outline

**CV** (`examples/{typst,markdown}/sarah-connor-cv.{typ,md}`):
